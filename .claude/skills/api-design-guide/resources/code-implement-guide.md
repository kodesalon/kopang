# Kopang 도메인 주도 아키텍처 및 설계 가이드 (code-implement-guide.md)

이 문서는 Kopang 시스템의 핵심 비즈니스 로직을 구현할 때 반드시 준수해야 하는 도메인 설계 및 아키텍처 규격입니다. 모든 코드 구현은 프레임워크에 종속되지 않는 순수한 비즈니스 로직 유지를 최우선으로 합니다.

## 1. Domain POJO와 JPA Entity의 분리

비즈니스 로직을 수행하는 순수 자바 객체(Domain)와 데이터베이스 영속성을 담당하는 객체(JPA Entity)를 엄격하게 분리합니다.

* **분리 목적 (Why):** JPA `@Entity`는 기본 생성자 강제, `final` 클래스 사용 불가 등 기술적 제약이 따르며 데이터베이스 테이블과 강하게 결합합니다. 이를 분리함으로써 도메인 모델은 프레임워크 기술에 종속되지 않고 객체지향적인 표현의 자유를 얻습니다.
* **구현 제약 (Trade-off & Solution):**
    * JPA Entity 분리로 인해 영속성 컨텍스트의 변경 감지(Dirty Checking)를 도메인 객체에서 직접 사용할 수 없습니다.
    * **[필수]** 상태 변경 로직이 수행된 후에는 Service 계층에서 반드시 `repository.update(...)` 혹은 저장 메서드를 **명시적으로 호출**해야 합니다.
    * 코드가 늘어나는 번거로움이 있으나, 명시적인 호출을 통해 비즈니스 상태 변경 흐름을 더 명확하게 파악하는 것을 지향합니다.

## 2. 의존성 역전 원칙 (DIP) 및 패키지 구조

`domain` 패키지 하위에는 순수 POJO 형태의 객체만 존재해야 하며, 외부 프레임워크(Spring, JPA 등)에 대한 의존성을 최소화해야 합니다.

* **인터페이스 위치:** Service 객체에서 영속성 계층(DB)이나 외부 인프라(PG사 API 등)에 접근해야 할 경우, 구현체가 아닌 **인터페이스**를 통해 접근합니다.
* **[필수]** 이 통신을 위한 인터페이스(예: `OrderRepository`, `PaymentClient`)는 인프라 패키지가 아닌, **`domain` 패키지 하위의 관련 도메인 패키지 내부에 위치**해야 합니다.
* 구현체(Implementation)는 별도의 `infra` 또는 `storage` 패키지에서 해당 인터페이스를 구현(implements)하는 방식으로 의존성을 역전시킵니다.

## 3. 도메인 객체(Aggregate) 설계 및 분리 기준

도메인 객체를 설계할 때는 **'데이터의 변경 주기'** 와 **'책임의 범위(생명주기)'** 를 최우선 기준으로 삼습니다. 무분별한 객체 참조를 지양하고 응집도를 높이세요.

* **분리 기준 (Different Lifecycle):** 변경 성격과 주기가 다른 데이터는 철저히 분리합니다.
    * *예시:* `상품(Product)` 정보와 `재고(Stock)` 정보는 변경 주기가 극명하게 다르므로 별도의 도메인 객체로 분리하여 설계합니다.
* **결합 기준 (Same Lifecycle):** 생명주기가 동일하여 강력한 정합성 보장이 필요한 데이터는 하나의 단위(Aggregate)로 묶어 설계합니다.
    * *예시:* `주문(Order)`과 `주문상품(OrderProduct)`은 생성 및 취소의 생명주기를 함께하므로, 주문을 루트(Root)로 하여 하나의 묶음으로 설계하고 영속화 시에도 정합성을 보장합니다.
