# 모킹 전략 및 테스트 대역 가이드 (mocking-strategy-guide.md)

무분별한 모킹은 시스템 구조와 강결합되어 내부 구현만 리팩터링해도 테스트가 실패하는 '깨지기 쉬운 테스트(Fragile Test)'를 유발합니다. 우리는 실제 객체 사용을 지향하는 고전파(Classicist) 방식을 원칙으로 하며, 아래의 규율을 엄격히 따릅니다.

## 1. 테스트 대역(Test Double)의 올바른 이해와 용어 정리

'모킹(Mocking)한다'는 표현은 상황에 따라 모의 객체 프레임워크를 사용한다는 행위를 뜻하기도 하고, 특정 대역(Mock)을 뜻하기도 하므로 아래의 5가지 분류를 명확히 인지하고 목적에 맞게 사용하십시오.

* **Dummy:** 매개변수 목록을 채우기 위해 전달되지만 실제로 사용되지는 않는 객체.
* **Spy:** 실제 객체의 동작을 유지하면서 호출 여부나 상호작용 정보를 몰래 기록하는 객체.
* **Stub:** 의존하는 객체로부터 특정 값을 받아야 할 때, 사전에 준비된 하드코딩된 답변을 제공하는 객체.
* **Mock:** 행위 검증을 위해 호출 및 상호작용을 기록하고 검증하는 객체.
* **Fake:** 실제 구현과 비슷하게 동작하지만 프로덕션에는 적합하지 않은 객체 (예: 인메모리 DB).

## 2. 고전파(Classicist) 지향 및 제한적 모킹

* **실제 객체 우선 사용:** 도메인 정책이나 비즈니스 로직 검증 시 SUT(System-Under-Test)의 모든 협력자(Collaborator)는 가능한 한 실제 인스턴스를 주입하여 사용하십시오. `MockK` 등을 활용하여 `every {... } returns...` 형태로 상세한 내부 구현을 스터빙하는 행위를 극도로 제한합니다.

* **제한적 테스트 대역 허용 구간:** 오직 다음 상황에서만 제한적으로 프레임워크 기반의 스터빙이나 대역 객체를 허용합니다.
    1. 외부 공통 사용자 서버, 결제 PG사 등 제어권 밖의 시스템 연동 시 (장애 전파 차단 및 비결정적 통신 제어).
    2. 현재 시간(`LocalDate.now()`), 난수 생성 등 실행 시점마다 결과가 달라지는 비결정적 로직 제어 시.
    3. 인프라를 교체해야 하는 경우 (인메모리 기반 데이터베이스를 **Fake** 객체로 활용).

## 3. 테스트 데이터 중앙화 (test-fixtures 전략)

* **산발적 데이터 생성 금지:** 회원, 주문, 상품 등 복잡한 도메인 엔티티를 생성하기 위한 장황한 준비(Arrange) 코드를 개별 테스트 클래스마다 중복해서 작성하지 마십시오.
* **팩토리 메서드 활용:** 여러 모듈에서 공통으로 사용되는 객체는 반드시 `test-fixtures` 모듈 내에 관리되도록 하세요.
* **최소 덮어쓰기 원칙:** 현재 테스트 맥락(Context)을 명확히 드러내기 위해 필요한 1~2개의 필드 값만 명시적으로 덮어쓰기(Override)하고, 나머지는 유효한 기본값(Default)으로 채우는 방식을 강제합니다.
