# 도메인 정책 테스트 설계 가이드 (domain-policy-test-guide.md)

이 문서는 시스템의 핵심 비즈니스 규칙이 담긴 도메인 객체(Entity, Value Object)의 정책이 올바르게 동작하는지 단위 테스트로 검증하기 위한 규격입니다. 도메인 정책 테스트는 가장 빠르고 결정적(Deterministic)이어야 하며, 시스템의 비즈니스 명세서 역할을 수행해야 합니다.

## 1. 프레임워크 독립성 (순수 POJO 테스트)

* **스프링 컨텍스트 로드 금지:** 도메인 객체는 인프라나 프레임워크에 의존하지 않는 순수한 자바 객체(POJO)로 설계되어야 합니다. 따라서 테스트 클래스에 `@SpringBootTest`나 `@ExtendWith(SpringExtension.class)` 등의 어노테이션 부착을 엄격히 금지합니다.
* **빠른 피드백 루프:** 의존성이 없는 순수 단위 테스트이므로 수천 개의 테스트도 수 초 내에 실행되어야 합니다(FIRST 원칙 중 Fast).

## 2. 경계값 중심의 파라미터화 테스트 (Parameterized Test)

* **경계값 분석(Boundary Value Analysis):** 비즈니스 정책(예: 주문 최소 금액, 결제 한도 초과 여부 등)을 검증할 때는 정책이 나뉘는 경계값을 중심으로 성공/실패 케이스를 촘촘하게 검증하십시오.
* **`@ParameterizedTest` 적극 활용:** JUnit 5의 `@ParameterizedTest`와 `@ValueSource`, `@CsvSource` 등을 활용하여 중복 코드를 제거하고 다양한 입력값에 대한 도메인 정책을 한 번에 문서화하십시오.

## 3. 살아있는 문서화 (Living Documentation)

* **비즈니스 용어 사용:** 테스트 메서드 이름과 `@DisplayName`에는 개발 용어(예: `return_true`, `check_logic`)가 아닌 기획자나 도메인 전문가가 이해할 수 있는 비즈니스 정책의 문장 형태로 작성하십시오.
* **행위 중심 검증:** 도메인 객체의 내부 상태(필드값)를 직접 꺼내어(Getter) 검증하기보다는, 도메인 객체에게 메시지를 던져(메서드 호출) 그 객체가 스스로 올바른 판단을 내리는지(행위)를 검증하십시오.

## 4. 협력자(Collaborator) 처리 원칙

* **실제 객체 사용 (고전파 지향):** 도메인 로직 검증 중 다른 도메인 객체(VO 등)와 협력해야 한다면, `Mockito.mock()` 등을 사용하지 말고 **실제 객체**를 생성하여 주입하십시오. 순수 자바 객체 간의 결합은 모킹의 대상이 아닙니다.
