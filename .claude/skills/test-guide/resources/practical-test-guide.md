# 실용적 단위 및 학습 테스트 설계 가이드 (practical-test-guide.md)

이 문서는 통합 및 인수 테스트 작성이 비효율적이거나 불가능한 예외적 상황에서, 코드의 신뢰성을 확보하기 위해 실용적으로 단위 기능을 검증하고 외부 기술 요소를 학습하는 테스트 작성 규격입니다.

## 1. 부분 기능 테스트 (Partial Function Test) 전략

기존 테스트가 없는 레거시 시스템이나 복잡한 흐름 내부에 수명이 짧은 이벤트성 기능을 추가할 때, 전체 인수 테스트 작성 비용이 산출 가치보다 크다고 판단될 경우 적용합니다.

* **테스트 용이성을 위한 의존성 역전:**
  로직 내부에 숨겨진 제어 불가능한 요소(예: `LocalDate.now()`, `Random`, 전역 상태 등)는 반드시 메서드 파라미터로 분리하여 외부에서 주입받도록 리팩터링하십시오. 이를 통해 특정 시간이나 조건에 종속되지 않는 결정적(Deterministic)인 테스트를 작성할 수 있습니다.
* **제한적인 가시성 확장 (`@VisibleForTesting`):**
  부분 기능을 격리하여 테스트하기 위해 `private` 메서드를 `internal` 또는 `public`으로 열어야 할 경우, 반드시 `@VisibleForTesting` 어노테이션을 부착하십시오. 이는 해당 코드가 설계적 응집도 때문이 아니라 순전히 테스트 목적으로 가시성이 조정되었음을 팀원들에게 명시하는 약속입니다.
* **트레이드오프와 남용 경계:**
  이러한 부분 기능 테스트는 비즈니스 생명 주기가 짧거나 영향 범위가 국소적인 경우에만 허용됩니다. 선착순 주문이나 결제 처리와 같은 시스템의 핵심 도메인은 반드시 `acceptance-test-guide.md`의 규격에 따라 전체 여정을 검증해야 합니다.

## 2. 학습 테스트 (Learning Test) 작성 규격

우리 시스템의 비즈니스 로직이 아닌, 외부 라이브러리나 프레임워크(예: Jackson `ObjectMapper`, Redis 명령어 동작, Kafka 컨슈머 설정 등)의 동작 방식을 명확히 이해하고 검증하기 위해 작성합니다.

* **실행 가능한 기술 문서화:**
  학습 테스트는 팀원들이 특정 외부 도구를 어떻게 이해하고 활용해야 하는지 보여주는 레퍼런스 역할을 합니다. 클래스명에 `LearningTest`를 명시하고, 테스트 메서드명은 해당 도구가 어떻게 동작해야 하는지 직관적인 문장형으로 작성하십시오.
* **프로덕션 코드와의 완전한 분리:**
  학습 테스트 내부에서는 우리 프로젝트의 비즈니스 서비스나 유즈케이스 클래스를 호출하지 마십시오. 오직 순수한 외부 도구의 API만을 활용하여 환경을 통제하고 Assert(검증)를 수행해야 합니다.
* **버전 업그레이드 방어선 활용:**
  작성된 학습 테스트는 추후 외부 라이브러리의 버전 업그레이드 시 하위 호환성이 깨졌는지 즉각적으로 파악할 수 있는 훌륭한 방어선이 됩니다. 따라서 검증 로직(Assert)은 도구의 핵심 스펙을 정확하게 짚어내야 합니다.
