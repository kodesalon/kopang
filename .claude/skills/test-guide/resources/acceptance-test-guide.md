# 서버 인수 및 통합 테스트 설계 가이드 (acceptance-test-guide.md)

이 문서는 시스템의 안정성과 CI/CD 파이프라인의 실행 속도를 보장하기 위해 유스케이스 및 인수 테스트 작성 시 반드시 준수해야 하는 규격입니다.

## 1. 테스트 환경 최적화 및 컨텍스트 추상화

* **단일 커스텀 어노테이션 사용:** 테스트 컨텍스트의 캐싱을 극대화하여 실행 속도를 높이기 위해, 개별 테스트 클래스마다 `@SpringBootTest` 등을 다르게 조합하지 마십시오. 모든 통합 테스트는 반드시 프로젝트에 정의된 `@AcceptanceTest`만 사용해야 합니다.
* **지연 초기화(Lazy Initialization) 대응:** 빠른 테스트 구동을 위해 `spring.main.lazy-initialization=true`가 기본 설정됩니다. 보안 클래스 등 즉시 로드가 필요한 빈으로 인해 실패가 발생하면, `LazyInitExcludeConfiguration`에 명시적으로 제외 필터를 등록하십시오.
* **[주의] 컨텍스트 캐싱 무효화 요인 억제:** 개별 테스트 클래스 내에서 `@MockBean`, `@SpyBean`, `@TestPropertySource`, `@ActiveProfiles` 등을 추가로 선언하면 스프링 컨텍스트가 새로 구동되어 테스트 시간이 기하급수적으로 늘어납니다. 공통 컨텍스트를 최대한 유지하십시오.

## 2. 데이터베이스 격리와 트랜잭션 정책

* **`@Transactional` 롤백 안티 패턴 금지:** 데이터 정리 목적으로 통합/인수 테스트에 `@Transactional`을 부착하는 것을 엄격히 금지합니다. 이는 운영 환경과의 트랜잭션 경계를 다르게 만들어 데드락 및 Lazy Loading 오류를 은폐합니다.
* **JSON 픽스처 및 리스너를 통한 생명주기 제어:** 데이터 세팅은 SQL 파일 대신 유연한 관리가 가능한 JSON 포맷을 사용하십시오. `@AcceptanceTest(setUpScripts = ["...json"])` 형태로 주입하고, `AcceptanceTestExecutionListener`를 통해 테스트 실행 전 데이터를 `INSERT`하고, 종료 후 물리적으로 `TRUNCATE` 해야 합니다.

## 3. 블랙박스 통신 (리팩터링 내성 확보)

* **프로덕션 DTO 클래스 직접 사용 금지:** API 엔드포인트 검증 시(예: RestAssured 사용), 요청 Body를 구성할 때 프로덕션 코드의 DTO를 인스턴스화하지 마십시오.
* **원시 타입 및 자료구조 활용:** 내부 구현 노출을 막고 완벽한 블랙박스 테스트를 유지하기 위해, 언어 기본 자료구조(`Map` 등)를 활용하거나 순수 JSON 문자열을 생성하여 요청하십시오. 이를 통해 비즈니스 로직 변경 없이 내부 구조만 리팩터링할 때 테스트가 깨지는 것을 방지합니다.

## 4. 테스트 대역 (Test Double) 사용 기준

가급적 실제 환경과 동일한 '실제 객체(Real Object)'를 사용하는 것을 원칙으로 하되, 불가피한 경우 아래의 기준에 따라 테스트 대역을 선택하십시오.

* **외부 서비스 연동 (제어 불가):** 통신 자체가 비결정적이거나 테스트 환경이 없는 경우, **Fake 객체**를 구현하여 대체하십시오. (예: 결제 PG사 연동 모듈)
* **비즈니스 외적 부수효과 (알림 등):** 알림 발송, 메신저 연동 등 부수효과가 발생하는 로직은 빈 동작을 수행하는 **Dummy 객체**로 대체하십시오.
* **상태 재현이 극도로 어려운 경우:** 특정 시간 경과, 복잡한 선행 조건 등 데이터 셋업이 지나치게 어려운 경우에 한해서만 모의 객체 프레임워크(MockK, Mockito 등)를 활용해 **Stubbing** 하십시오. (단, 앞서 언급한 컨텍스트 재생성 이슈에 유의하여 공통 설정으로 빼는 것을 고려하십시오.)
