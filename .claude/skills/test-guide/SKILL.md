서버 테스트 전략 표준 가이드를 활성화했습니다.
현재 요청받은 작업이 단위 테스트, 인수 테스트, 통합 테스트 등 서버 품질 검증 코드의 작성 및 수정과 관련 있다면, **코드를 작성하기 전에 반드시 아래 네 문서를 먼저 읽고 그 규칙을 100% 준수**하여 코딩을 진행하세요.

1. **인수/통합 테스트 환경 및 작성 규칙**: `resources/acceptance-test-guide.md`
2. **테스트 대역(Mock) 및 픽스처(Fixture) 활용 규칙**: `resources/mocking-strategy-guide.md`
3. **부분 기능 및 학습 테스트 작성 규칙**: `resources/practical-test-guide.md`
4. **도메인 정책 단위 테스트 작성 규칙**: `resources/domain-policy-test-guide.md`

### 핵심 테스트 설계 철학 (반드시 반영할 것)
- **가치 판단 우선:** 모든 계층(Controller, UseCase, Domain)에 대해 기계적으로 테스트를 생성하지 마십시오. 비즈니스 핵심 가치에 집중하고, 수명이 짧은 이벤트성 기능은 최소한의 검증만 수행합니다.
- **실용성 (통합 검증 지향):** 관리해야 할 테스트의 절대적인 양을 줄이기 위해, 가능한 한 단일 인수/통합 테스트 하나로 여러 계층을 동시에 커버하여 문서화 역할까지 수행하도록 작성하세요.
- **완전성과 간결성 (FIRST 원칙):** 작성된 테스트 코드는 그 자체로 하나의 완전한 문서여야 하며(Complete), 불필요한 노이즈 없이 간결해야(Concise) 합니다.

### 엄격한 출력 제약 조건 (토큰 및 컨텍스트 최적화)
가이드를 읽고 제약 조건을 반영하여 코드를 작성하되, 메인 세션의 리소스 낭비 방지를 위해 다음 규칙을 엄격히 지키세요.

1. 당신이 작성한 코드의 로직이나 설계 이유, FIRST 원칙 적용 여부 등을 채팅창에 절대 구구절절 설명하지 마세요.
2. 채팅창에는 오직 `✅ [테스트 대상 도메인/메서드명] - [수정/생성한 테스트 파일명] 작업 완료` 형태로 단 한 줄만 보고하세요.
3. 만약 상세한 의사결정 과정이나 실행 도중 발생한 에러 해결 작업 기록을 남기고 싶다면, 채팅창 대신 `docs/work-logs/` 디렉토리에 마크다운 파일로 조용히 작성하여 저장해 두세요.
